# Executor context：待验证的上下文补充方案

状态：待观察，未实施；先积累真实使用样本，再决定是否需要增加。

## 决策与 Why

当前先保持 Consult 的上下文构建、Advisor prompt 和事件字段不变。通过已有 events 关联 transcript 做事后整体评估，不要求 Advisor 每次自评触发必要性或输入充分性。

候选方案要解决的是「执行记录里没有交代的环境和约束」，而不是增加更多历史正文。顾问可能知道主模型做过什么，却不知道当前工作目录、哪些工具实际启用、任务是否禁止推送等边界。如果这些信息只存在于主模型的运行环境或注入规则中，不能依赖它们碰巧进入会话摘要。

但缺口存在不等于值得新增机制：信息也可能已在用户消息或 why 中充分表达；复制整份 system prompt 会重复背景、增加输入，并混淆执行者规则与顾问职责。先验证实际影响，再付出上下文与维护成本。

## 候选方案边界（非实施承诺）

- 首先考虑确定性的少量环境事实：cwd、主模型与 thinking level；在现有工具清单标记启用状态，不另复制一份工具清单。
- 本次关键约束优先由 why 明确表达，不另建需要维护的规则摘要。不自动复制或摘要整个 system prompt、AGENTS.md、skills。
- 如后续确需独立背景块，应标记为执行者背景参考，不覆盖 Advisor 自身的无工具、只返回建议等职责。
- 新增背景块暂以 500 tokens 作为候选工程预算，而非信息完整性保证；具体限额与计数方式待实施前确定。超限优先删重复说明，不静默截断关键约束，也不把不完整摘要宣称为完整规则。
- 不带完整环境变量、目录树、依赖清单或 git diff；不承诺能低成本、无损地从所有注入规则中自动挑出重要约束。

## 事后如何判断必要性

以新事件契约生效后的跨任务样本为主，通过 `session + toolCallId` 关联 Consult 前的当前分支、顾问回复、CONSULT-LOG 与后续执行结果。旧记录中回填的标签单独看，不与原生采集的效果标签混作同一质量的证据。

复盘重点：

1. **有没有发生可归因的缺口**：顾问是否因不知道 cwd、工具可用性或任务边界而给出不适用建议；主模型是否随后因这些原因拒绝、修正建议或返工。
2. **缺口在哪里**：信息已在 transcript 中却被忽略、被 compaction/provider 转换丢失，还是从未发送给顾问。只有最后一类直接支持新增 Executor context；前两类应优先改善聚焦或转换路径。
3. **最小补充是否能解决**：补一句 why 是否足够，还是相同的确定性环境事实反复缺失、值得自动提供。关注问题后果及跨任务重复性，不只看次数。

`confirm` 占比、`adopted` 与 `adoptionEffect` 用于筛选样本，不直接证明触发合理或输入不足；blocked/failed/cancelled 与完成建议分开分析。事件只提供索引和行为信号，不能脱离 transcript 判断输入质量，也无法覆盖「本应咨询却没有咨询」的漏触发。

Transcript 可帮助重建执行链路，但不保证还原当时最终发送给 provider 的完整请求，尤其是历史运行环境与转换后的截断。证据不足时标为未知，不假定当时环境等于现在。

## 复评出口

- 未发现重复且有实际后果的缺口：维持现状。
- 主要是 why 不够明确或顾问忽略已有证据：调整聚焦提示，不增加背景块。
- 反复缺少相同环境事实并导致错误建议：只补被证据支持的最小字段，再比较收益和新增输入量。
- 项目约束缺失造成高后果风险：单独设计规则来源、信任边界与完整性保障，不用全量复制 system prompt 代替设计。
