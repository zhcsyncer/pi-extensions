# 三模型独立评审与 Pi 1.4 后续判断

输入：[逐扩展变更审计](./integration-change-review.md)固定`da15c88`，产品仍是`24ac1da`对`f48a91b`。三个指定模型分别研究，没有互看报告；之后主会话分别质疑其具体推论，原稿保留，修订追加。这里不是多数票批准，更不是自动回撤指令。

模型：`xai/grok-4.7`、`cursor/opus-5.5`、`ollama-cloud/kimi-k3`。正式开发图仍为SDK1.2，本机来源与依赖没有升级；对1.4只做官方发行/源码调查，未安装或运行。

## 结论先行

**不应把整个分支作为“升级必需”交付，也不建议整体退回所谓最小集。** 保留真实行为修复和能减轻维护的整理；把用户可见政策和额外展示能力单独审阅；内部无影响的一行小加固不值得再为删而删。

用户直接升级1.3没有明显问题，与证据相容：多数旧普通路径本来能跑，很多差异只有特定调用、恢复或费用记录形状才会触发。但触发少不能反证权限边界、状态持久化和合法日志消费不重要。

这里区分两种“最小”：

- **从main重新做一遍的最小补丁**：只修具体破坏的契约，很多重构可不开始。
- **面对已经集成的候选，怎样减少风险**：撤回也是改动；要看能否独立拆除、会失去什么承诺，而不是把第一种最小集机械套回来。

## 哪些具体推论被否决或收窄

### 1. Tool Display丢ctx是真实契约缺口，但不是整套重写的通行证

旧`createBuiltinToolBase`会收到ctx，并用ctx.cwd选内置工具；真正丢的是**向底层execute转发的第五参**。所以不能说普通读写路径都错了。

SDK1.3的Bash只有收到ctx才注入Pi会话/模型环境变量；Read也借ctx.model决定非视觉提示和图片缩放选项。旧包装还未完整保留outputSchema等定义字段。这是具体可描述的静态行为损失，不只是“内部结构不够优雅”。主会话复核了旧包装和实际1.3工具实现。

但本轮没有旧/新完整离线正控，Opus的单次评审子进程env观察也有加载路径混杂，**不标成所有用户的已实测事故**。修复执行保真可以很小；官方renderer接入的大改另有统一晚到工具、减少包装耦合的维护价值，不借此全部升级为必需。

导航标记也是独立契约：自绘用户消息不能只剥掉宿主OSC标记却不恢复。这个理由与消息框owner或样式隔离无关。

### 2. codemode未启用，不等于可以丢掉已承诺的嵌套边界

codemode默认要显式开启，但任意扩展的ctx.executeTool也可产生嵌套调用。配置观察与本仓直接调用检索只限制“目前已知使用面”，不能证明所有合法调用方都不可达。深层展示仍是可选增强；子任务权限与Todo恢复一旦支持这条路径，就应兑现承诺。

因此保留Subagents公开tool_call门禁和Todo的一行限制，不套用到所有工具。也不能把来源匹配简化成仅看名字：独立合同有“扩展覆盖builtin read应拒绝、真正builtin read应通过”的正负控，名字相同不等于被授权的那个工具。

### 3. 取消结算有实际收益，不因它是SDK既有行为就变得多余

根tool result在message_end一次落盘，仍在执行的前台嵌套Agent，其最终费用和收据必须在那之前收齐。窄屏障解决的是这个时序，不只是改一个内部状态。

代价也要留：provider不结束时，取消等待可能被拖住。本轮没有因此再造全局调度器或多层超时；已返回ID的后台任务、取消get等待不应纳入这道屏障。1.4的worker排队管的是“何时启动脚本”，没有证据表明它替代这个结算问题。

### 4. 合法公开接口不能仅因夹具构造就被判成假需求

Meter缺getEntryCount的分支消费的是公开ReadonlySessionManager允许的形状；实际宿主恰好给更宽对象，只能说明默认快路径不受影响。默认不付出扫描成本的3行回退，删除几乎没有收益。

同理，负金额输入不是真实账单事故样本，但负数拉低本地预算是明确行为。保留小的读侧过滤合理；不必为它再建复杂迁移框架，也不与权限漏洞混成同等紧急度。

### 5. Meter的新捕获目标需要如实说明

旧实时路径主要采样事件；新路径会在启动和持久边界补读会话记录，补上标准usage和观察间隙。启动回填是更强的完整性目标，确实带来来源/旧行识别的维护负担，不能都说成旧默认路径已经坏掉。

但锁和去重也不是全由新架构自造：旧live与手动import原本就可能并发，旧import全量重写可能覆盖新增行。不能仅凭“采用另一种架构更轻”就删掉现在相互依赖的半套逻辑。

已有合同覆盖legacy、live/import顺序、可读来源fork及并发追加；没有据此把一切迁移风险宣称消除。优先检查一个具体旧格式变化，不要求无差别复制用户真实账本。

### 6. 找到了一个具体迁移缺口，而不是继续假设“也许会重计”

Opus提出Consult空洞槽位的候选问题后，主会话核对了旧/新源码，并只允许对这一个差异做纯函数离线对照。复制的是固定提交的真实parser及两个本地依赖，未改实现，没有使用真实账本。

旧parser先过滤没有usage的顾问槽位，再用过滤后序号作sourceId；新parser采用原始下标。旧行已有sourceId，因此新匹配器不会使用“旧行无sourceId”的payload回退。结果：

| 合法合成输入 | 应有记录金额 | 真实旧/新解析、匹配、折叠后的结果 |
|---|---|---|
| 前一顾问无usage，后一顾问0.02；同一次调用旧账已记录 | 0.02，不应新增 | 仍新增0.02，折叠后0.04 |
| 无空洞，同一次调用 | 0.03，不应新增 | 不新增，仍0.03 |
| 全新的toolCallId，新增0.03 | 两次共0.06 | 正确新增，共0.06 |
| 前一顾问无usage，后两顾问0.02/0.03 | 0.05，不应新增 | 旧/新:1还会匹配到不同顾问，最终新增0.03，折叠后0.08 |

这表明当前**旧账匹配逻辑有具体兼容缺口**，不是“任何迁移都可能坏”的泛泛猜测。合法槽位来自顾问在获得响应前失败/取消而没有usage的情况；没有测其出现频率。

**边界**：只调用真实旧`usageRecordsFromMessage`/`parseSession`及新`usageRecordsFromSessionEntry`/`diffRecords`/`collapseDuplicateRecords`。没有运行完整SDK首次启动、store序列化往返、readAll或预算聚合，更没有证明用户真实账本已受影响；“0.02→0.04”是夹具在解析/折叠层的金额，不是服务商扣款。首次捕获静态上走同一legacyMatching路径。

**建议优先级**：这项应先作窄兼容修正及旧格式往返验收，再批准Meter身份迁移的发布；不要求因而重写整个捕获层，也不把它归因于SDK1.4。本轮只报告，未修代码。

证据：`/var/tmp/pi-integration-independent-review/meter-consult-migration/`中的`REPORT.md`、`results.json`、`run.initial.log`和源文件/探针SHA；一次离线运行、两个对照正常，两个空洞案例违反“不重复新增同一消耗”的预期，结果未覆盖重跑。

## 新版Pi：优先利用上游收益

官方latest已核实为**1.4.0**，本地发布时间**2026-10-22 06:48**；比1.3新增的稳定发行只有这一版。Node仍>=22.19.0，TypeBox仍1.3.27。完整变化与引用见[Pi 1.4调查](./pi-1.4-upstream-review.md)。

更值得关注的直接收益：

1. 并行codemode满容量时排队、并发弹层不再把先前Promise悬挂。
2. 长摘要不再撞固定输出上限；截断恢复同时清理孤立工具结果，不让后续会话持续400。摘要输出可能变长，费用也可能增加。
3. 对应provider的按需工具加载保住缓存前缀，以及空白工具输出、临时错误识别、CJK/终端问题由宿主统一修。

当前维护包TS源码未发现对telemetryContext、被删的getPiUserAgent、旧resolveTranscriptTools字段或before_provider_headers的直接引用，**没有找到新的硬迁移落点**。这不是1.4测试已通过；有价值的是做少量相关隔离验证，不是先写一轮新兼容层。

## 执行边界

本次没有修改产品、依赖、独立合同、全局来源或配置，也没有升级SDK、连接真实服务或操作真实账本；唯一新执行是上述纯解析层定向对照。本地保存三份独立原稿、追加修订、官方版本响应和定向核验记录。Opus初次曾对本机设置及有限会话文件做只读元数据观察；后续禁止继续读取用户历史，相关数字不被外推为普遍可达性证据，未复制用户账本。
